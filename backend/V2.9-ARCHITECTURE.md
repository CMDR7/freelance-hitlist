# FL-HL V2.9 // Persistent Acquisition & Complete Retrieval

Status: Implementation foundation — schema proposed in feature branch  
Baseline: V2.8.0  
Canonical pipeline: acquisition → canonical normalization → deduplication → source balancing → response limiting

## Objective

Remove the practical 100-record ceiling from the user experience without removing the API's per-response safety limit. A client requests up to 100 records per page and follows an opaque cursor until the snapshot is exhausted.

V2.9 also introduces scheduled acquisition, D1 persistence, and operational diagnostics.

## Non-negotiable invariants

- Keep the established six configured sources; source expansion requires separate approval.
- Preserve URL canonicalization, normalization, semantic/URL deduplication, provenance, attribution, freshness and source balancing.
- Do not bypass or reorder the canonical pipeline.
- Maximum response page size remains 100.
- Pagination reads a stored acquisition snapshot; it must not reacquire external feeds for every page.
- A degraded source does not automatically make the overall pipeline run fail.
- No public administrative mutation endpoints.
- No deployment until local verification and production configuration review are complete.

## Proposed D1 model

Migration: backend/migrations/0001_v29_initial.sql

### pipeline_runs

One row per scheduled or manual acquisition. Stores start/end times, duration, overall state, acquisition/normalization/deduplication/return counts and errors.

### source_health

One row per source per run. Stores source type, endpoint, status, HTTP status, latency, candidate/parsed counts, check time and error. This allows source-level degradation to be distinguished from overall pipeline health.

### opportunities

Current canonical opportunity records, keyed by the existing SHA-256-derived canonical ID. Structured fields are retained for filtering and diagnostics; record_json preserves the complete normalized response contract.

### pipeline_run_opportunities

Immutable membership and order for each acquisition snapshot. ordinal is assigned only after source balancing. This is the stable pagination surface.

### latest_payload

A singleton pointer to the latest completed snapshot, with record count and pipeline metadata. The previous pointer is replaced only after a successful snapshot has been written.

### pipeline_state

Small key/value operational state, such as last successful run and retention watermark.

## Acquisition transaction

1. Create a pipeline_runs row with running status.
2. Acquire from the existing four RSS feeds and two API connectors.
3. Record per-source status, latency, raw candidate count, parsed count and error.
4. Normalize and deduplicate using the existing canonical module.
5. Source-balance the complete normalized collection.
6. Upsert canonical opportunity records.
7. Insert pipeline_run_opportunities rows with stable ordinals.
8. Mark the run success or partial depending on source outcomes and pipeline completion.
9. Update latest_payload only after snapshot membership and run metrics are complete.

A failed run must not replace the latest successful payload pointer. Use D1 batch/transaction semantics for the final persistence phase. Ensure run cleanup/rollback behaviour is explicit in implementation tests.

## Cursor pagination contract

Route: GET /api/opportunities?live=true&limit=100&cursor=<opaque>

- limit: integer 1–100; default 50.
- No cursor: resolve the latest completed snapshot.
- Cursor: identifies the immutable run_id and last returned ordinal.
- Next page: query the same snapshot where ordinal > lastOrdinal, ordered ascending, with LIMIT pageSize + 1.
- hasMore: true only when the extra row exists.
- nextCursor: opaque encoding of snapshot ID and last returned ordinal; null at end.
- Response count: number of records in this page.
- Response total: snapshot record count before request filters.
- Include snapshotRunId and generatedAt so the client can detect snapshot changes.
- Reject malformed cursors with HTTP 400. If a cursor's snapshot has expired, return HTTP 410 rather than silently switching snapshots.

The API's maximum page size remains 100. The frontend accumulates pages and prevents duplicate canonical IDs.

### Filtering

Search and region filters must be applied before the page limit, not after page retrieval. Store normalized search_text and region_text fields so the first implementation can use parameterized SQL predicates. Avoid interpolating user input into SQL. Preserve current substring-match semantics unless tests demonstrate a deliberate compatibility change.

## Schedule

Target cadence: every 12 hours. Cloudflare Cron Triggers use UTC. Proposed expression: 0 */12 * * *.

The Worker must implement scheduled(controller, env, ctx). Scheduled invocations call the same acquisition/persistence service as an explicitly permitted internal/manual test path; public GET endpoints remain read-only. Do not add a public mutation route to trigger acquisition.

## API and diagnostics

Keep current read-only endpoints compatible:
- /api/health
- /api/feeds
- /api/connectors
- /api/sources
- /api/sync/status
- /api/opportunities

Add read-only diagnostics as required by the existing V2.9 project specification. Diagnostics should expose pipeline freshness, run state, per-source health, latency, candidate counts, normalization/rejection, deduplication, source balancing, validation and last error.

## Frontend integration

- Fetch the first page on initial load and refresh.
- Append subsequent pages on explicit load-more or controlled infinite scroll.
- Keep existing filters, source context, sorting, detail modal and telemetry functional.
- Reset accumulated pages when query/region/filter context changes.
- Bind all pages to one snapshot run ID; if the snapshot expires, refresh from page one with a visible refresh state.
- Keep total available count distinct from currently loaded count.

## Retention

Retain a bounded history of run diagnostics and snapshot membership. Initial policy proposal: 30 days for run history and snapshot membership; current canonical opportunities remain until superseded or a separately approved lifecycle policy removes them. Cleanup must never delete rows referenced by latest_payload. Confirm expected D1 storage and limits before enabling cleanup.

## Verification gates

1. Apply migration locally and inspect schema/indexes.
2. Unit-test cursor encoding/decoding, invalid cursor handling, stable ordering, last page and expired snapshots.
3. Test page boundaries with 0, 1, 99, 100, 101 and more than 200 records.
4. Test deduplication across sources and verify attribution/provenance survive persistence.
5. Test source degradation while other sources succeed.
6. Test that failed/partial persistence does not replace latest_payload.
7. Test query/region filters before pagination and no duplicate IDs across pages.
8. Test scheduled handler locally with the configured cron.
9. Verify frontend aggregation, filters, counts and detail modal.
10. Only then review D1 remote binding and production Cron Trigger deployment.

## Current implementation boundary

This branch establishes the D1 schema and design contract only. It does not yet change the Worker, frontend, production bindings, schedule, or deployed service.
